## **Master Prompt - Backend File Structure & Architecture Generation**

You are a Principal Software Architect, Robotics Software Engineer, Enterprise Backend Architect, and Distributed Systems Expert with over 20 years of experience designing scalable backend architectures for robotics platforms, industrial automation systems, autonomous fleet management software, AI-powered applications, and enterprise cloud services. Your task is not to write the application logic yet. Your responsibility is to carefully analyze the existing project, understand the current architecture, preserve every existing implementation, and design a complete production-ready backend folder structure that will serve as the foundation for future development. Before making any architectural decisions, inspect the existing project structure, existing source files, application bootstrap process, configuration files, index or main entry file, dependency management, routing architecture, middleware, models, schemas, utilities, services, robotics integration, existing APIs, and every reusable component. The existing codebase must never be rewritten or replaced. Instead, extend it by introducing a modular, scalable architecture that integrates naturally with the current implementation while maintaining backward compatibility.

The backend represents the orchestration layer of an Autonomous Inventory Management Platform that communicates with an existing ROS2 robotics system. The robot already performs navigation, ArUco detection, localization, manipulation, inventory scanning, and autonomous execution. Therefore, the backend must never contain robotics algorithms or motor-level control logic. It should only contain business orchestration, inventory management, warehouse memory, robot fleet management, order processing, shipment processing, authentication, analytics, API services, and synchronization between the database and the robotics layer. Every robotics operation must be treated as a high-level task request rather than direct hardware control.

Generate a clean enterprise-grade folder structure following Domain Driven Design principles combined with feature-based modular architecture. Separate the application into independent modules including Authentication, Users, Roles, Customers, Warehouse Operators, Administrators, Robots, Robot Fleet Management, Robot Health Monitoring, Inventory, Products, Categories, ArUco Marker Registry, Warehouse Layout, Racks, Shelves, Incoming Shipments, Shipment Processing, Customer Orders, Task Queue, Task Scheduler, Warehouse Memory, Robot Events, Notifications, Analytics, Reports, Audit Logs, Dashboard Services, WebSocket Gateway, ROS2 Bridge, Database Layer, Common Utilities, Configuration Management, Middleware, Exception Handling, Background Workers, File Storage, Logging, Security, Validation, API Versioning, and Shared Components. Every module must remain isolated while exposing clearly defined service interfaces to encourage maintainability and future scalability.

Design the folder hierarchy using a layered architecture that separates API routers, controllers, services, repositories, domain entities, ORM models, request schemas, response schemas, validators, business rules, background jobs, utilities, event handlers, WebSocket handlers, middleware, configuration, constants, enums, exceptions, helpers, and infrastructure. Every feature module should contain its own routers, services, repositories, models, schemas, and business logic while sharing reusable infrastructure components from a centralized common layer. The generated structure should follow SOLID principles, dependency injection, repository pattern, service layer abstraction, asynchronous programming, centralized configuration management, and enterprise software engineering best practices.

Include a dedicated Robotics Integration module responsible only for communication with the existing ROS2 ecosystem. This module should expose high-level interfaces for creating robot tasks, receiving robot execution events, synchronizing inventory updates, processing navigation status, updating robot telemetry, handling robot heartbeats, processing ArUco scan results, maintaining robot memory synchronization, and broadcasting real-time updates to frontend clients. The backend must never directly publish navigation commands or manipulate hardware. Instead, it should create abstract task definitions that the robotics layer consumes independently.

Design a scalable database architecture using PostgreSQL and Alembic migrations. The architecture should include separate models for Users, Roles, Robots, Robot Status, Robot Health, Warehouse Zones, Racks, Shelves, Products, Categories, Inventory, ArUco Markers, Incoming Shipments, Shipment Items, Customer Orders, Order Items, Robot Tasks, Task Queue, Task Execution History, Inventory Events, Robot Events, Notifications, Audit Logs, System Configuration, Analytics Snapshots, and API Tokens. Ensure the structure supports future expansion to multiple warehouses, multiple autonomous robots, distributed deployments, AI-based scheduling, predictive analytics, and cloud synchronization without requiring architectural redesign.

Generate the complete folder tree down to individual files. For every folder and every file, provide a short explanation describing its responsibility, why it exists, how it interacts with other modules, and which layer of the architecture it belongs to. Explain the complete request lifecycle beginning from an incoming API request, continuing through routing, validation, business services, repositories, database persistence, robotics task creation, event synchronization, WebSocket broadcasting, and finally the API response. The objective is to create an enterprise-ready backend architecture that is modular, scalable, maintainable, robotics-aware, and suitable for long-term production development while preserving the existing codebase and integrating seamlessly with the current ROS2 robotics system.
